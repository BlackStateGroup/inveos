# Field dispatch, manual shift records and handover

Implementation branch: `feat/field-dispatch`, stacked on Field sessions `9a235c921ee878ddd6959829cd9651ad838be92f`. Root has integrated that predecessor and owns combined acceptance, review and merging. This increment implements the docs02 P1 supervisor dispatch, team check-ins, configurable prompts, shift records, manual incident status and recipient-acknowledged handover in the existing browser/API/Field system. It does not claim native, physical-device, safety-response, production or entire-product completion.

## Connected workflow

1. In existing case work, assign an actual task to an existing current investigator/reviewer. A current case reviewer opens Field, saves current scope, loads assigned tasks and prepares dispatch instructions for a different named task owner. This does not add membership, reassign the task or grant any permission.
2. The reviewer supplies a title, instructions, up to eight prompts, explicit timezone-qualified acknowledgement/check-in/shift deadlines and a reason. The exact publication request is saved encrypted before sending. Publication retains its identity, expected publisher, exact task revision, current authority/access versions, named recipient, actor and server time. Replay and history lookup recover a lost publication response. Each revised/closed/cancelled publication appends a new version; recipient/task identities remain fixed. Reassignment uses explicit cancellation plus a new existing assignment/dispatch. Closed/cancelled revisions can retain a removed recipient's historical name; active publication requires current membership and exact assigned task ownership.
3. The named recipient inspects and explicitly saves published instructions in the encrypted vault. They can manually acknowledge or decline the exact instruction version and answer its prompts. Publication is not acknowledgement. A publishing reviewer cannot acknowledge their own dispatch. Changed instructions require a fresh acknowledgement record.
4. The recipient starts a normal persisted Field session through the existing session workflow. Check-ins, incident accounts and handovers link that actual author-owned session and optionally an exact observation capture/version in it. A check-in is a manually declared working/paused/finished status and prompt answers. Incident states are manually declared needs-attention/update/resolved accounts. None acquires a location, sends an alert or asserts safety.
5. Save each operation as a frozen JSON original in the encrypted operational queue. Deliver the original through the separate operational-original API, then explicitly apply it to the dispatch. Separate original/application receipts distinguish local-only, original received and status applied. Missing session dependencies, stale instructions/task versions, revoked devices, scope changes or failed requests retain all originals and request history. Exact receipt lookup and exact-ID retry resolve lost responses.
6. Offer a handover to a different current case member, with retained contents and actual session/task/optional-observation links. Only that named independent recipient can acknowledge/decline the exact current handover original. Acknowledgement does not transfer case access, task ownership or safety responsibility. The existing case-work handover/task controls remain separate; this is a linked Field shift record, not a silent edit to case work.
7. Append corrections/withdrawals to the exact preceding operational capture and version. Author, record kind, stable record identity and handover identities cannot be silently changed. Incident/check-in/handover corrections can explicitly use newly published current instructions after a fresh acknowledgement; their prior versions remain in history. An instruction acknowledgement cannot be repurposed across instruction versions. Correcting a handover creates a new exact target requiring its own recipient acknowledgement.
8. The supervisor refreshes the case board. It shows manually acknowledged/declined status, check-in receipts, late receipt markers, explicit overdue state and stale dispatch reasons at a labelled server snapshot time. Overdue uses saved deadlines and server receipt/application presence, not device source-time claims or assumed movement. Expired/stale/cancelled/closed instruction scope does not assert a current overdue state. Historical unresolved incident and pending handover records remain counted across instruction revisions; a new publication does not quietly resolve them. Full shift/publication/correction history is retained.

There is no polling, background tracking, automatic location, covert collection, external messaging, live alert delivery or safety-response guarantee. Session completion, task completion, finding approval, source-use decisions and client release are not inferred from operational status.

## Storage, authority and receipt boundaries

Migrations116–117 add append-only dispatch publication versions, operational originals and applied records. Migrations118–119 are unused; migration115 remains root-owned. Publications pin existing `case_work_revisions`, case authority, membership and access versions. Current case locks serialize publication/task/scope decisions. Active publication and each new application recheck the publishing reviewer's current case role, the recipient's current membership, collection state, exact task version/owner and authority/access. Clients and nonmembers cannot access these routes. Application additionally rechecks the current versioned Field device/grant through existing `checkGrant`; raw operational intake uses existing `checkFieldAcceptance`, including independently approved exact-original recovery when needed. Publication itself is an online current-reviewer action; it does not claim hardware attestation or require a native device.

Operational bytes use the existing configured immutable original store/encryption adapter, but **do not create an evidence row, claim, finding or Field evidence-capture row**. Their raw manifest, original/device/source times, hash and original receipt are stored in `field_dispatch_originals`; application is a separate append-only row in `field_dispatch_records`. Native Field session/observation originals remain in their existing evidence store and are linked as existing case records only. Link resolution checks exact case/session/version identities; it does not turn a status into evidence or assert fresh byte integrity for linked historical observations. Root's separate read-only source inspector owns those deeper session inspections.

Each application receipt retains the complete original receipt, original structured record, current application authority/reason, applied version and server time, actual task revision, session ID and optional observation version/digest. Current membership is checked for historical readback. Same-input replay/receipt GET may recover an already committed historical action after its grant/device became stale; that does not accept additional bytes or a new status. New raw acceptance and new application remain fenced. Reused request IDs with different bodies fail. Competing corrections fail explicitly without overwriting the original.

Existing session/capture receipts are neither reconstructed nor narrowed here. Their optional root-added `fieldProvenance` survives unchanged through vault backup/restore/identity replacement. New operational receipt objects are also stored wholesale. Dispatch does not claim report-export provenance for an operational status.

All DB changes and their audit records commit together. Raw original delivery is intentionally separate from status application: an application/audit failure can leave an acknowledged original with no applied status. Original writes use a unique immutable object per attempt. If storage succeeds but the DB transaction fails or its outcome is unknown, the unreferenced object is retained rather than risking deletion after an ambiguous commit. Bounded orphan reconciliation, object-store lifecycle/retention integration and operational monitoring remain acceptance/operations work; this build adds no production cleanup or deletion control. New retries can create another storage object while keeping the same logical original identity.

## Encrypted offline integration

The existing `inveos-field-v1` IndexedDB database is upgraded to schema version2 by adding an `operations` store. Existing config, capture and context stores are preserved byte-for-byte. No new dependency or native storage architecture is introduced. Old open tabs are closed by the existing version-change handler; a blocked upgrade requires closing them. Older app code cannot open the upgraded database as version1 and must not be used as a rollback by clearing browser storage.

The new store uses the same passphrase-derived nonextractable AES-GCM key, authenticated identity/revision envelopes, bounded records and compare-and-swap writes. It contains original operation bytes/manifests, full receipts, exact application/recovery request snapshots and recent attempt history; reviewer publication requests; and explicitly saved versioned instruction copies. Instructions are retained by dispatch version, not silently overwritten by a later publication. The offline instruction cache includes up to20 latest operational record summaries with an explicit truncation notice; full server history and this vault's own originals remain separately available. An oversized encrypted copy fails visibly without deleting the previous copy. Forms are not durable until explicitly saved.

Encrypted backup formatv2 authenticates all four stores and their inventory. Empty-vault restore accepts legacy v1 backups and restores an empty operations store; v2 backups require the complete authenticated operations inventory. A v2-to-v1 format edit is rejected rather than silently dropping operations. Replacement-device re-encryption includes operations, instructions and publications with the same revision/identity checks as existing captures. Original bytes, old device/authority claims, source times and full receipts remain unchanged. Backup time is not source, ingest or application time.

Lost-device recovery uses the existing retained-manifest recovery API and independent Field reviewer controls. Operational manifests are labelled `field-operation-...` and remain distinguishable from evidence capture. A replacement target grant is saved explicitly, the original owner submits the exact old manifest, another current reviewer decides it, and raw delivery checks that decision and current target again. Application still needs current dispatch/task/instruction authority. Raw receipt lookup should precede recovery when delivery may already have committed. A later unnecessary recovery request cannot replace an existing immutable original receipt.

When an original was never applied and its instruction version is stale, the UI can prepare a **new** current-instruction original from retained text, with a reason referencing the old capture ID and another explicit scope confirmation. It does not pretend the old original was applied/corrected, and the old version is fenced from applying to the new instructions. Current-version delivery uncertainty uses receipt lookup/exact retry instead. No control deletes an original or silently changes its manifest.

## API and bounds

All paths below use `/api/cases/:caseId`, authentication/current case membership and CSRF on writes.

| Method | Route | Function |
| --- | --- | --- |
| GET | `/field-dispatch-options?after=<uuid>` | Existing assigned task options, 50 per page |
| POST | `/field-dispatch` | Current reviewer publishes exact versioned instructions or explicit close/cancel revision |
| GET | `/field-dispatch?before=<uuid>` | Case board, 20 dispatches per page, persisted status/deadline summaries |
| GET | `/field-dispatch/:dispatchId` | Complete bounded publication and operational history |
| POST | `/field-dispatch-originals` | Accept exact immutable operational bytes/manifest separately from evidence |
| GET | `/field-dispatch-originals/:captureId/receipt` | Verified original receipt recovery |
| GET | `/field-dispatch-originals/:captureId/original` | Audited hash-verified operational-original download |
| POST | `/field-dispatch-records` | Apply an acknowledged original under a current grant/instruction/task boundary |
| GET | `/field-dispatch-records/:captureId/receipt` | Exact application receipt recovery after original verification |

Bounds:500 dispatch identities per case;100 instruction versions;5,000 raw operational originals per case;500 applied records per dispatch including all correction versions;100 versions per operational record;8 prompts and answers;6,000-character account/instructions;256KiB raw original. Local operations store:100 total entries (publications, instruction-version copies and originals),400,000 bytes per authenticated envelope,10 application requests and10 recovery identities per original,20 recent attempt summaries. Existing capture/context bounds remain unchanged. Backup input bound is165MB for the three bounded encrypted data stores plus config/inventory. Capacity errors preserve prior state; save encrypted backups before storage pressure. No automatic record eviction is implemented.
