# Case collaborators and ownership

The case-access increment implements the following bounded policy. Exact executed verification and merge status belong in BUILD_HANDOFF.md. It does not complete provider or contractor acceptance.

The current internal case owner may add/remove existing internal tenant members and transfer ownership to an existing internal case member. Case membership provides access to the current internal workspace under the member's existing tenant role; this interface must not create identities, change tenant roles, admit client roles to internal content or authorise client disclosure. Owner status does not confer reviewer powers. Existing members can inspect the current case team and retained access decisions. Only the owner can enumerate eligible internal tenant colleagues or change access. The current owner cannot remove their own membership; ownership must first be transferred. Transfer retains the former owner's explicit membership until separately removed.

Each change requires a reason, stable request UUID and expected access version. Retain immutable events with actor/subject attribution and server time. A legacy checkpoint records the observed owner at migration time without inventing historical grants or decisions. Current case/tenant/role/owner checks precede replay: an old request must not restore revoked access. A lost transfer response is recoverable by reading the saved team/history as the former owner, if still a member. Access changes share the case lock used by intake, work, review and worker-authority checks; waiting writes must recheck membership after obtaining that lock.

Removing a member must preserve their work, evidence, authorship and audit history. Later requests, search, assigned-work queues, mentions, jobs and internal exports must observe revocation. Already downloaded data cannot be recalled; an in-flight read authorised before revocation is not an instant-purge guarantee. Existing disclosure eligibility continues to check its author/reviewer memberships, so removing a reviewer may make a release unavailable. This interface must explain that effect rather than silently promising unchanged releases.

Existing provider binding/provisioning, actual provider/MFA acceptance, invitation delivery, tenant-level role administration, emergency owner recovery, contractor least-privilege policy and external security/privacy approval remain open. No external messages, billing or production database action are authorised by this increment.

## Bounds and reproduction

The team, eligible-candidate and immutable history routes return at most 50 rows, with UUID or version cursors. New grants cap a case at 200 collaborators; changes cap at 1,000 access versions. Locks have a 2-second deadline and statements a 5-second deadline. Pages are current authorised views, not frozen snapshots. Candidate pages return existing internal names, UUIDs and roles only; no email directory is exposed.

Open Brief → Case collaborators in the persistent lab. The owner can find eligible colleagues, record a reasoned grant/removal/transfer, inspect retained history and refresh. Unchanged submission retry recovers a committed grant/removal; transfer recovery requires refreshing because the former owner no longer has management authority. No unsent form content is saved across reloads.

Run the API workspace suite against disposable PostgreSQL using the restricted application role, `npm run lint`, `npm run build` and `npm run test:foundation`. Actual loopback HTTP checks cover tenant/case/client/non-owner/current-role denial; PostgreSQL checks cover conflicts/restart, audit rollback, immutable history, ownership transfer, paging, retained work, revocation across search/queues/discussions/originals and worker leases. A real lock-wait regression first reproduced a work write committing after revocation; the shared case lookup now rechecks membership and the request's role in a fresh SQL statement after acquiring the lock. Existing worker operations already acquire the case lock before their separate permission query.

`INVEOS_TEST_BROWSER=1` requires a working Chromium sandbox. The browser acceptance exercises a lost committed grant response, retry, reload/history, ownership transfer, revoked workspace clearing and 390px layout. Do not treat this test description as proof it ran; retain exact CI and render evidence in the handoff.
