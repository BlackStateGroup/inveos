# Reviewed case entities and relationships

This bounded WP-10 journey records case-scoped entities and explicit, source-linked relationship interpretations. It does not infer identity equivalence, source truth, wrongdoing or a client release. Ambiguous entities can share a label and remain separate records. No graph runtime, new dependency, external collection or copied research code is introduced.

## Stored interpretation and review

Migration 036 stores separate entity heads/revisions, relationship heads/proposals, typed source joins and independent review decisions. Entity kinds cover people, organisations, assets, places, incidents and documents. Labels and identity uncertainty can be corrected or withdrawn with a reason. The entity kind and original identity/author remain fixed. Earlier records are append-only.

A relationship proposal pins both entity identities, versions, kinds and labels, plus one to five distinct reviewed text/document findings. Each source includes the canonical verified finding fingerprint and authority version. Saving, inspecting and accepting sources uses the existing original/derivative/citation/correspondence/interpretation verification path; it does not trust client-supplied quotes. A separate assigned reviewer who has authored **no version** of that relationship may accept or reject the exact proposal digest/version with a reason. One immutable decision is retained per proposal. A revision starts a new candidate and retains earlier decisions. Withdrawal preserves the history even when a source has become unavailable.

Entity correction/withdrawal, inactive case or changed authority makes an otherwise accepted edge need fresh review. Listing the graph explicitly reports `not_checked_on_listing`: source bytes and later document-correspondence decisions are freshly checked only during source inspection, proposal save and acceptance. An old recorded decision is not a fresh integrity assertion. Rejection can record the inability to rely on an unavailable source. Graph interpretations are separate from source findings, reports and disclosures; this increment does not add graph content to report exports.

## Access, bounds and UI

Every route requires a current internal session and tenant/case membership. Mutations require CSRF/origin checks; clients cannot read/write internal graph records. Composite foreign keys bind endpoints and typed source findings to the same case. The application role can update only the head version; history/source/review rows reject update/delete. Case locks, expected versions and atomic audit prevent conflicting or partially recorded decisions. Stable creation retries return the latest record, including withdrawal. Review retries retain the exact recorded decision.

The graph is bounded to 200 entity identities, 400 relationships, 100 revisions per identity and five sources per proposal, with two-second SQL statement deadlines. These are bounded development limits, not representative production capacity acceptance. Case search includes labelled entity/relationship metadata. Diagram layouts are local grid/circle choices; positions are not evidence. Neighbourhood queries remain within the case. The HTML record list, exact source inspector, history and review controls provide alternatives to diagram navigation. Source time, receipt time, extraction/review time, page/box and UTF-8 offset basis remain explicit. Access denial clears loaded graph, sources, histories and editors.

## Reproduction and acceptance

Use the existing disposable lab instructions and migrate with `npm run db:migrate`. Run `npm run lint`, `npm run typecheck`, `npm run build` and `npm run test:foundation`. Set the disposable restricted/admin PostgreSQL URLs documented in the repository and run `node --import tsx --test --test-concurrency=1 apps/api/test/*.test.ts`. Focus graph API acceptance with `--test-name-pattern='^graph ' apps/api/test/api.test.ts`. Set `INVEOS_TEST_BROWSER=1` only on a supported sandboxed Chrome host. Hosted Checks retains `case-graph-browser`; do not weaken the sandbox locally.

Tests exercise exact source/entity binding, duplicate labels without merging, self-review denial, immutable historical decisions, conflicting edits/reviews, authority/revocation/tenant/client denial, original corruption, changed document correspondence, deliberately altered database provenance, audit rollback, hard query limits and restart. The browser journey creates records/proposals, verifies source inspection, independent acceptance, reload, stale review after correction, historical labels, narrow-screen overflow and clearing revoked data. Exact executed revisions and results belong in BUILD_HANDOFF.md; unrun browser checks are not acceptance.

Document API fixtures in this journey use first-party deterministic derivative records to test provenance joins. They are **not actual parser benchmarks**. Existing isolated supplier native/OCR/raster acceptance remains separately recorded. Representative graph performance, richer query/filter/pattern analysis, cited AI/media intelligence and independent professional/security/privacy acceptance remain separate requirements in the canonical plan.
