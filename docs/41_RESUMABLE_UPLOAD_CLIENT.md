# Resumable upload client

Synthetic lab, 27 October 2026. The evidence file form now drives the existing reservation/chunk/finalisation API. No server schema, dependency, parser or evidence contract change.

Each attempt reselects and hashes the complete bounded file (still 256 KiB maximum), then recovers the same reservation by its persisted idempotency key. It queries received ordinals and sends only missing exact 32 KiB ranges. Reservation identity, case, size, chunk size, authority version, expiry representation and received range shape are checked before proceeding. Chunk acknowledgements must include the submitted range without forgetting earlier ranges. Final evidence receipts still pass the existing original digest/metadata/quarantine validator before the pending key is removed. Server permission, expiry and full-digest verification remain authoritative.

Progress shows server-acknowledged bytes and reservation expiry, not verified final evidence. Pause aborts current transport and stops before the next request; navigation also aborts local transfer. An in-flight request may already have committed, so retry reconciles server state rather than assuming cancellation. Pause does not delete staging or cancel the reservation. Completion response loss recovers the same original without resending chunks. No automatic background transfer or retry loop is installed.

New chunk operations use a distinct `:chunks-v1` tab-storage namespace. If an older whole-file pending record exists, the UI continues that exact original endpoint and key first. Converting such a record into a new reservation could duplicate an already committed original, so it is deliberately forbidden. A corrupt legacy record blocks new intake until investigated. Only retry key/fingerprint are persisted, never file bytes or metadata. Reselect the same file and re-enter the exact metadata after navigation/reload. Tab loss/new sign-in and duplicated tabs have the limitations documented in `39_RECOVERABLE_BINARY_INTAKE.md`; this is not durable offline/device storage.

Use the existing lab and approved fictional case, then Evidence → Register a binary original. Choose a file, source timestamp with timezone and acquisition method. During transfer, Pause leaves acknowledged ranges resumable. Submit the same selection and metadata again to resume. Browser file-picker/navigation/pause/accessibility acceptance remains unrun; UI compilation and Node helper execution do not replace it. Expired/cancelled reservations require explicit handling; an expiry/cancellation UI and bounded administrative maintenance remain open.

Verification: `npm run lint`, `npm run typecheck`, `npm run build`, `npm run test:foundation`, `node --import tsx --test apps/api/test/chunk-upload.test.ts`; run `npm test --workspace @inveos/api` with disposable PostgreSQL credentials. Three helper scenarios cover missing-range selection/pause, malformed or foreign receipts/provenance/ranges, and legacy routing. A new actual HTTP/PostgreSQL scenario deliberately drops one committed chunk acknowledgement and then the completed-original acknowledgement, reconstructs client state and recovers one reservation/one original with identical downloaded bytes and no duplicate chunks. Hosted receipt pending in BUILD_HANDOFF.md. No real network outage, browser, device, power-loss, parser or restore result is claimed.

Rollback restores the previous UI; retain pending records and immutable originals. New chunk keys must be recovered through the reservation API rather than interpreted as old direct-intake keys. No migration reversal, source redistribution, merge or deployment.
