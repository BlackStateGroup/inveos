## Reproduced findings and fixes

1. **Invoice session revocation was checked only at request authentication.** A GET waiting on the case row returned 200 after its session was revoked. The invoice transaction now checks the existing session predicate at entry and before commit, and repeats current case/role access. A late compilation test verifies rollback of invoice head, revision, lines/reservations and audit, followed by an exact retry under a fresh session.
2. **Invoice compilation could commit after the declared recipient lost its client role during audit.** It returned 200 with a stale-recipient warning in the newly created invoice. Current declaration/recipient, authority, source revisions, reservations and verified expense originals are now checked again after compilation and successful review writes. This reuses the existing source/declaration validators. Historical snapshots and exact operation receipts remain retained; no billing/release policy is added.
3. **Composition transactions retained stale access snapshots.** The inherited repeatable-read transaction returned composition data after session revocation during a real case-lock wait. Composition operations now use case-serialized read-committed transactions with current session/access checks before return. Tests also remove case membership during the wait. Other report transactions retain their existing snapshot behavior.
4. **New composed freezes accepted a reviewer who no longer had case access.** Removing the accepting reviewer's membership still allowed a new frozen report. New composition freezes now verify the exact active outline/review and current accepting reviewer before work and after audit, plus final source-use proofs. A late removal rolls back the frozen report and audit. Existing frozen bytes and exact committed retries remain available under ordinary caller access; historical review records are not rewritten.
5. **Collaborator publication outlived the publishing reviewer's case access.** Recipient detail still returned 200 after the publisher was removed. Shared discovery/detail/final eligibility now requires that current case reviewer. A different current independent reviewer may explicitly republish the retained instructions. Submission review also requires current grant eligibility and repeats it after audit.
6. **Collaborator pagination disclosed an inaccessible grant ID.** With 26 published grants and subsequent internal-only handling, discovery returned no items but a non-null cursor naming a hidden grant. The bounded scan now produces cursors only from visible grants, validates recipient cursors and fails closed if the scan bound cannot establish the next page. Internal pagination remains bounded.
7. **Task-template application did not recheck acceptance after the final audit.** Removing the accepting reviewer while the application audit waited still committed all work and its receipt. Acceptance and selected internal owners are now rechecked after audit. Regression coverage checks both reviewer and owner loss, complete rollback, and exact retry after restored eligibility. Previously committed application receipts retain their historical semantics.
8. **Feedback's final release gate omitted source-use revalidation.** A recipient request committed after the source-use/metadata reviewer lost case membership during the feedback audit. The final gate now uses the same frozen-report source-use verifier as disclosure delivery, including current handling, and repeats current session verification. The failed operation leaves no feedback head/revision/audit; exact retry after eligibility restoration creates one request. Client errors remain generic and cause the existing UI to clear unavailable release state.

The first four regressions failed against the inspected base (four unexpected 200 responses). Cursor, template, feedback and invoice-recipient regressions were run before their respective fixes and failed as described. These are application/API observations, not claims about production exploitation.

## Hosted race-test investigation

Root reported the case-budget and task-status-batch wait tests failing at `4216ad12c0d778849409100d6a061016236387b3`. Both failures were reproduced in a separate detached worktree: 0 passed, 2 failed, 8.246 seconds. The tests matched `FOR UPDATE OF c` in `pg_stat_activity.query`. That older expanded query places the phrase at offset 1234 while this server's `track_activity_query_size` is 1 kB. The API was waiting, but the observer could not see the suffix.

The tests now assert that an `inveos_app` connection is blocked by the exact fixture connection via `pg_blocking_pids`, independent of SQL text truncation or generic preflight query shape. The case lock, membership/role changes in the locking transaction, expected rejection and zero-mutation assertions remain. With only these assertion changes, both tests passed on the old revision in 6.883 seconds. Both original tests also passed on unmodified `8d58c956` in 9.397 seconds. Logs: `/tmp/inveos-old-races-before.log`, `/tmp/inveos-old-races-after.log`, `/tmp/inveos-review-races-before.log`.
