# Frozen internal report review

28 October 2026. Draft implementation stacked on PR #24. This is internal snapshot review, not client release, current-source verification or production acceptance.

An assigned reviewer other than the user who froze the revision may record `accept_internal` or `request_changes` against its exact SHA-256. The server rehashes frozen bytes, requires current active approved case authority for a new decision, and records the authority version at decision time separately from the historical report's source policies. Changed case authority does not rewrite the snapshot or its source policies. A future release gate must independently check current scope, privilege, redaction and recipient permissions; these decisions never grant client access.

The decision, trimmed 10–2,000-character rationale, reviewer, fingerprint, revision and timestamp are append-only. One decision per reviewer/revision is the natural retry key: exact retries return the original receipt, changed retries fail 409. A new report revision is required for a revised decision. Different reviewers may disagree; no aggregate approval or automatic precedence is inferred. Case locking serialises simultaneous requests; decision and audit commit atomically. The author cannot self-review either decision. Existing case/tenant/internal-role checks govern reads and writes. The API cannot prove a person actually read the report.

Routes: `GET` and `POST /api/cases/:caseId/report-revisions/:revisionId/reviews`. POST requires CSRF and `{sha256,decision,reason}`. GET returns `items` with the explicit `internal_review_not_release` status; more than 50 reviews fails closed instead of silently truncating. Responses are no-store. Migration 014 adds the append-only review table and scoped foreign keys; originals and frozen report bytes are unchanged.

The Saved internal report revisions panel provides review history and a form. The browser must first successfully verify/download that revision before enabling the form, and the reviewer must attest that they inspected it. This UI gate is not server-side proof of human inspection. Server author/role checks remain authoritative. The current demo sign-in is normally the freezing author and will be denied; tests create a separate fictional reviewer through the existing harness. No production identity or invitation flow is added.

Privacy: rationales are internal case data, displayed as text and included in scoped audit context; use minimal fictional explanations. No new dependency, upstream source or licence approval. Rollback routes/UI together; keep append-only reviews and audits, never delete decisions as a code rollback. Author/reviewer separation is a deliberately stricter internal gate; it does not constitute legal sign-off.
